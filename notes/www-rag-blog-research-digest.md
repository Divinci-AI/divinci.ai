## 1. What WWW-RAG is and why it exists

WWW-RAG is Divinci's system-owned, publicly browsable RAG corpus of the open web — a from-scratch crawler ingests public websites, embeds their pages, and publishes each site as its own queryable/chattable vector under a public directory (`divinci.ai/www-rag`). It started as two intertwined efforts: (1) a **gemma-gem browser extension** path where users' own browsing contributes page context in real time, and (2) a **standalone Rust crawler** (`www-rag-router`) that runs an unattended day/night pipeline crawling, embedding, and publishing sites at scale, independent of any user's browsing. The second effort is now the dominant one and the subject of this digest: ~93-98 real websites (philosophy archives, government/space agencies, docs sites, law, SaaS company sites, e-commerce demos, UFO-report archives, and more) crawled, deduped, chunked, embedded, and served as individually-chattable, publicly-listed AI assistants — each site gets its own release, welcome message, conversation starters, and (where extractable) theme, with retrieval-quality safeguards evolved through a long chain of real production incidents.

## 2. Scale / current numbers

- **92 sites, 92 releases, 129,931 chunks** as of the 2026-07-03 WWW-RAG Directory launch (`GET /api/v1/www-rag-directory`).
- Grew to **93-94 turso-libsql vectors** (93 corpus hosts + 1 on-demand) by 2026-07-01 after a full-corpus audit/reconciliation; **98 sites** referenced later (nutritionfacts.org, Attio.com additions push past 97-98).
- Local crawl corpus scale (Rust prototype benchmarking phase): **21 real websites, 7,880 chunks** — the harness's proving ground before the full 90+-site production corpus.
- Router/routing microbenchmarks: routing latency stays **µs-scale** (mean 60µs, p99 156µs at N=21 centroids) regardless of corpus size; embedding inference dominates wall-clock (~83-125ms per query) — the router itself is never the bottleneck.
- Local disk footprint (as of 2026-07-03, still growing): `.turso/` (local libSQL DBs, one per host, pre-publish cache) = **14GB across 96 hosts**, unbounded/ongoing growth; `okf/` (raw crawl bundles, source of truth) = 2.4GB; repo total ~18GB. Individual DB sizes: `en_wikipedia_org.db` 2.5GB, `www_gutenberg_net_au.db` 1.9GB, `iep_utm_edu.db` 885MB.
- Notable per-site yields: nutritionfacts.org 13,825 chunks (1500 pages, subdomains+render); Attio.com 1,028 pages → 2,833 chunks across 7 crawled hosts/subdomains in one crawl (attio.com 794 pages, docs.attio.com 209, atlas.attio.com 18, + trust/build/api subdomains); perldoc.perl.org dropped from 33,251 → 5,035 chunks after de-duplicating an 84.9%-duplicate footer block; man7.org settled at 116 chunks post-crawl-engine-hardening; arxiv.org proved crawlable only after a chain of memory/OOM/durability fixes (see incidents).
- Corpus minimum-similarity threshold for web-crawl chunks: **0.40** cosine (web-crawl chunks naturally score ~0.40-0.46, vs the platform's 0.62 default — every hit was being filtered until this was patched).

## 3. Architecture decisions

### Build vs. buy: bespoke Rust crawler vs. platform-native Web Crawl Connector — STATUS: dual-track, deliberately
Two crawler paths coexist and the choice between them has flip-flopped with real evidence:
- **Bespoke Rust crawler (`www-rag-router`)** — the production workhorse today. From-scratch BFS crawler (`src/crawl.rs`), same-origin by default (+ eTLD+1 subdomain mode), robots.txt-respecting, headless-Chrome (Brave) render-fallback behind a `--features render` Cargo flag. Runs entirely on a local machine (MacBook, day/night daemon), embeds via **local Ollama** (free), and pushes finished per-site Turso DBs to the platform. Deliberately decoupled from the monorepo (Mongo/Vectorize coupling) to move fast.
- **Platform-native Web Crawl Connector** — the customer-facing tenant feature (`ConnectorConnection`/`ConnectorSyncJob`, Connectors-page parity with Dropbox/GDrive). A 2026-06-22 design doc proposed migrating WWW-RAG onto this connector (`notebooks/2026-06-22-web-crawl-living-connectors-plan.md`) as "mostly wiring, not building" — reusing existing crawl execution (`crawlURL`), recurrence config, cron polling, webhook infra, and changelog rollup. All 5 phases were built, deployed, and live-verified by 2026-06-24 (staging + prod), including a working 6h auto-sync poll loop.
- **Migration attempt hit real blockers** (`notebooks/2026-07-05-web-crawl-connector-hang-noop-bug.md`): live-testing the connector against nodejs.org (motivated by the Rust crawler only getting 48 chunks for it) surfaced 3 error-swallowing bugs (hangs forever on large limits, false-positive instant "completed" on small limits) — all fixed and deployed (`20e1f4819a`). Then hit a deeper architectural wall: a live/published vector can't be written to directly (`isVectorUsed()` guard protects chat traffic), which is exactly the shape every already-published WWW-RAG site is in. Solved via an opt-in generic **draft-vector + swap-on-success** feature (`swapOnSuccess`, `3b13cb9ccf`) — crawl into a fresh unpublished draft, then atomically repoint the release on success. Then found WWW-RAG's own Directory/chat paths were reading a stale denormalized `WwwRagSiteModel.vectorId` field instead of resolving through the release, making the swap invisible — fixed by routing WWW-RAG through the same `resolveReleaseRagVectors` release-resolution path every other whitelabel's chat uses (`8f6e530099`). **Fully resolved 2026-07-05**, verified end-to-end against nodejs.org.
- **But rolling the connector out to the ~90 remaining sites immediately caused a real production incident** (see §4) — event-loop lag up to 112s p99 from firing too many crawls concurrently. A long chain of further incidents (CPU-bound synchronous parsing blocking the event loop, Cloud Run OOM kills, turso-libsql write failures, fire-and-forget promises dying silently on instance recycling) had to be fixed one by one before the connector was durable enough for even a single large site (arxiv.org).
- **2026-07-14 explicit decision: local-first, not connector-first, for our own bulk crawling.** The user clarified the agentic-recon crawler should run **locally** (MacBook → planned DGX Spark/AMD AI Halo machines), injecting into prod, rather than firing our own bulk crawls through the Cloud Run connector (the connector shares infra with the main customer-facing API — running our own bulk ingestion there risks customer-facing latency). The Web Crawl Connector remains a **customer-facing feature** (their own sites, small scale) — it is NOT the vehicle for scaling WWW-RAG's own ~90-site corpus. New crawler capabilities (subdomain crawling, JSON-LD product extraction) were built once for the connector, then explicitly **ported a second time** into the local Rust pipeline for this reason.

### Render-fallback tiering
Evolved to a **3-tier chain**: Cloudflare Browser Rendering (credits-covered, `/content` endpoint) → Firecrawl (anti-bot specialist, markdown+links format — needed because its markdown extraction handles div-built pages the block extractor can't) → local headless Brave (last resort). Verified live: CF-protected sites serve CF's own renderer a "Just a moment…" interstitial it can't solve itself; Firecrawl cracked a site that both other tiers failed on. An `is_challenge_interstitial()` guard rejects challenge-page junk from any tier, and `/cdn-cgi/*` paths are excluded from the frontier.

### Incremental crawl-graph design
Each site persists a `crawl-graph.tsv` (url→links) as a TSV file. `crawl_site(prior)` pre-seeds the visited set and resumes the frontier from stored-but-unfetched links, so capped sites deepen pass-over-pass while finished sites cost ~0 fetches on subsequent passes. `write_bundle_mode(merge=true)` adds new pages without wiping the bundle; `ingest-okf` skips bundles unchanged since the local DB's last build (mtime-based), avoiding a full re-embed on every pass. This is the mechanism that makes an unattended day/night loop economically viable — without it, every 3-hour pass would re-crawl and re-embed the entire ~90-site corpus.

### Embedding-model symmetry (the load-bearing economic bet)
Local Ollama `embeddinggemma` (768-d) was verified **bit-identical** (cosine similarity 1.0000 on test strings, both L2-normalized) to Divinci's cloud-served `@cf/google/embeddinggemma-300m` on Workers AI. This means embeddings computed for free on a laptop land in the exact same vector space the cloud platform already queries — no re-embedding step, no mismatch. This was independently re-proven in the separate PixelRAG/local-desktop-RAG project as a live "on-device embed → cloud Vectorize → cloud query → correct grounded retrieval" pipeline, reinforcing it's not a one-off coincidence. This fact is what makes the entire local-crawl-then-publish economic model work: embedding cost for a 90+-site, 130k+-chunk corpus is effectively $0 (only compute/electricity), versus paying per-token cloud embedding at that scale.

### Storage-layer choice: Turso/libSQL per-site DB, not Qdrant, not one shared index
The Rust prototype benchmarked three storage options for "one isolated index per website": Qdrant collection-per-site (the original design, works but is Qdrant's documented anti-pattern — caps at ~1,000 collections, ~0.29 MiB overhead each, dies at 1k-10k sites), a single-collection-with-payload-filter alternative (validated *faster* — 2.59ms filtered vs 4.54ms flat — but sacrifices physical isolation), and embedded libSQL/Turso DB-per-website. **Turso won**: it keeps true physical isolation at unlimited N (built for millions of mostly-idle per-tenant DBs, unlike Qdrant), measured 99.4% top-K / 100% top-1 retrieval agreement vs. the Qdrant baseline (DiskANN ≈ HNSW, recall-safe), and a disk-size concern was solved via `compress_neighbors=float1bit` (1.2GiB → 134MiB per index, and query agreement actually went *up* since quantization only touches graph-traversal copies, not the final f32 distance comparison). Qdrant was subsequently retired entirely from the prototype.

### Website-Segmented RAG Router design (the original novel idea)
Rather than one unified vector index, each site gets its own isolated mini-index; an in-memory centroid router (µs-scale) picks the Top-M most relevant sites per query and fans out in parallel, merging results. Key validated findings: single-centroid routing recall@1 76% (NL queries), recall@4 95%; multi-centroid sub-clustering is a modest, cheap win (76%→90% recall@1 at k=12 sub-centroids) but not a rescue; routing's pruning vs. a flat unified index is quality-neutral (92% chunk-coverage overlap, 18/21 queries identical retrieval, 0 judge losses on the 3 divergent queries). One notable false alarm: an early result claiming "en.wikipedia.org only routes correctly 1/8 of the time" turned out to be a **sampling artifact** (unstrided sampling grabbed only the first 8 chunks = unrepresentative nav-menu boilerplate); with strided sampling the real number was 7/8, and overall recall was 95% not 79%. Lesson pinned in the README verbatim: *"a reminder to measure the measurement."*

## 4. Incidents and what they taught us

This is the densest section — a long, honest, mostly-self-inflicted incident chain, each one root-caused with real evidence (not guessed), several requiring 2-3 rounds before the true cause surfaced.

### 4.1 Root/trailing-slash dedup bug — crawl-graph never marked pages "seen"
**What broke:** Crawl-graph keys were stored via `url.to_string()` (which keeps a trailing slash for root-path URLs) but every comparison against those keys used `normalize_url()`'d strings (seed dedup, outgoing `page_links`, frontier-seeding's `g.contains_key(l)`). **Root cause:** a string-representation mismatch — the same logical URL had two different string forms depending on whether it went through normalization, so lookups silently missed. **Effect:** root-ish pages could get re-fetched on *every single pass forever*, regardless of the "incremental" setting, and it defeated exhausted-host detection entirely (a host could never register 0-new-pages if its root page kept re-registering as "new"). **How found:** discovered while building the exhausted-host cooldown feature (below) — testing kept showing a host as never-exhausted when it should have been. **Fix:** normalize keys both at graph-load time (self-healing for all ~100 already-crawled hosts with zero migration needed) and at save time. **Verification:** a 4-pass isolated sandbox test — fresh crawl → host marked exhausted → skipped within the cooldown window → correctly re-checked after cooldown expiry. **Lesson:** when two code paths independently decide "is this the same key," any asymmetry in normalization is invisible until you specifically test the boundary case (root URLs) that triggers the divergent representation.

### 4.2 Exhausted-host cooldown (a durability feature, not a bug fix)
**What was built:** a host whose incremental pass finds 0 new pages *and* wasn't capped by `max_pages` gets marked exhausted (`crawl-graph-dir/exhausted-since.txt`); future passes skip it entirely — zero fetches, not just zero re-fetches — for 72 hours (`WWW_RAG_EXHAUST_COOLDOWN_HOURS`), then re-check. Capped hosts are never marked (they still have more content to find); a host that resumes publishing new pages clears its own marker. **Why it matters:** without this, a 90-100-host corpus's steady-state passes waste time re-walking the frontier of every fully-crawled site, every 3 hours, forever — this closes the loop toward true "incremental" behavior.

### 4.3 Render-fallback waste on binary release artifacts (llvm.org)
**What broke:** `SKIP_EXT` (the file-extension denylist that prevents the render-fallback tier from attempting to "render" non-HTML content) was missing `.xz`/`.sig`/`.tgz`/`.exe`/`.asc`/`.tif`/`.csv`/`.srt`/`.ps`/`.bmp` and several archive/installer-adjacent extensions. **Effect:** llvm.org's release-archive tree alone burned **412 wasted headless-Chrome render-fallback launches** in a single pass — each one a failed browser launch + Navigate-always-fails-on-binary cycle — making it "the biggest single contributor to that pass's Chrome-profile reap volume." (A later check on the same still-running pre-fix pass, ~22 hours further in, found the cumulative count had climbed to 1,672 — the site kept marching through the same waste pattern across its entire historical releases archive, version after version, until the daemon was restarted onto the fixed binary.) **How found:** the extensions added were sourced directly from that pass's actual failure log, aggregated by extension, top 11. **Fix:** extended `SKIP_EXT`, defensively adding same-category siblings of what was already covered (`.zip`/`.gz`/`.tar`), plus regression tests (`looks_like_page_rejects_binary_release_artifacts`, `_keeps_real_pages`) pinning every observed failure URL shape so it can't silently regress. **Lesson:** a denylist maintained by intuition ("what extensions are obviously not HTML") will always miss cases; mining the actual failure log for real observed URL shapes is a more reliable source than guessing categories up front.

### 4.4 Content-hash algorithm mismatch — freshness detection dead on arrival
**What broke:** the locked design decision was `sha256(normalizeVisibleText(text))` computed identically on both the extension and server sides, but the server-side crawler was never actually ported to that hash function — it computed `sha256(JSON.stringify({html, markdown, links}))` instead (categorically different input). **Effect:** `page-status.fresh` and `submit-url.hashFresh` were **always false**; the only working freshness signal was a blunt 24-hour TTL window, and the extension's `?hash=` parameter was dead weight. **How found:** code audit (not observed failure) — "0 server files use `normalizeVisibleText`". **A secondary correction later found the whole premise was moot for the connector's economics anyway**: `crawlURL` calls `chunkAndAddToVectors` *unconditionally* — the isNew/isUpdated/"same" hash flag was only ever *reported*, never gated re-embedding. The actual embed-skip gate was a pre-existing, independent file-level dedup (`md5(textContent)` in `createFile`) that worked correctly the whole time. **Lesson:** a documented "locked decision" can silently rot into fiction if the implementation never lands — verify code matches design docs periodically, especially for cross-team/cross-repo contracts (extension vs. server) where nobody owns the whole path.

### 4.5 Auto-publish dedup querying the wrong whitelabel (loop-durability bug)
**What broke:** `auto-publish-new.sh`'s "already published" check queried only the original shared WWW-RAG whitelabel, but by this point all ~90 sites had been migrated to their own per-site whitelabels — so the shared-WL query returned just ~5 vectors instead of ~90. **Effect:** the autonomous day/night loop would have treated ~84 already-live sites as brand-new and republished them as duplicate vectors on every future pass. **How found:** caught during the first real end-to-end exercise of the hardened crawler (Attio.com scrape), before the loop was turned fully autonomous. **Fix:** switched the "done" set to the public directory API (`GET /api/v1/www-rag-directory`), which lists every site by host regardless of which whitelabel backs it. **Lesson:** a dedup/idempotency check that hardcodes a resource location (a single whitelabel ID) silently breaks the moment the underlying architecture migrates (per-site whitelabels) — idempotency checks should query the same public-facing source of truth that consumers use, not an internal implementation detail.

### 4.6 Disk-space near-miss — not the crawler's own fault
**What happened:** system disk dropped to 6.8GB free during an active crawl pass — below the crawl loop's own 12GB safety floor (`WWW_RAG_MIN_FREE_GB`). **Root cause:** NOT the crawler's own corpus (only ~16.5GB total between the local Turso DBs and OKF bundles at the time) — it was ~60GB of unrelated, stale Docker images and build cache sitting untouched on the machine. **Fix:** `docker system prune -a --volumes` reclaimed 53.64GB. **Lesson:** the crawler's own disk-headroom guard did its job (would have paused crawl+ingest before corrupting local Turso DBs), but the guard's floor was almost breached by something entirely outside its control — a reminder that a resource guard protects against the *symptom* (low disk) regardless of *cause*, which is the right design, but doesn't substitute for periodically auditing what else is eating the same disk.

### 4.7 Binary re-exec gotcha — a 25+ hour crawl pass from a stale process
**What happened:** a single crawl pass ran 25+ hours, way beyond the normal few-hours-per-pass, because the exhausted-host and SKIP_EXT fixes (§4.1-4.3) had landed as source but the already-running crawl daemon process was still executing the *old* compiled binary — binaries are only re-exec'd at the start of a fresh pass, not hot-reloaded. **Fix:** manually stopped the daemon and the in-flight crawl, then relaunched to pick up the new binary. **Recovery cost:** low — each site's bundle is persisted incrementally as it finishes, so only the small in-flight batch (~10-16 parallel seeds) needed to be re-attempted; already-completed sites' data was untouched. **This compounds with a separate, independently-documented Cargo footgun** (`feedback_wwwrag_turso_binary_feature_gated.md`): the `turso`/`live` binaries are feature-gated (`required-features = ["turso"]` / `["render"]`), so a plain `cargo build --release` silently skips rebuilding them entirely — it "Finishes" successfully while leaving stale binaries on disk. A second trap compounds this: if the daemon is actively running the old binary during a rebuild, the atomic binary-replace fails (text-file-busy) but Cargo may still mark its build fingerprint as "built," so *even a later correct-flag build no-ops*. This bit hard on 2026-07-14 — unit tests passed (a fresh test binary compiled) while the live `turso ingest-okf` process kept running old code, silently. **Lesson:** in any long-running-daemon-plus-compiled-binary system, "my fix is committed and tests pass" is not sufficient evidence the running system reflects it — verify the actual running binary's mtime/symbol content, and always stop-rebuild-restart rather than trust a hot no-op-looking build.

### 4.8 Connector rollout: fixed-sleep pacing ≠ throttling (real prod incident)
**What broke:** `setup-connector-for-site.sh` paced the *API calls* that kick off crawls (20-30s apart) but each `POST .../connectors/web-crawl/start` returns 202 immediately (fire-and-forget) — so pacing the requests just meant a new multi-minute crawl+embed job started every 20-30s while prior ones were still running, and concurrency stacked unboundedly. By host #10-11 there were 7+ concurrent crawl jobs, each doing CPU-bound page parsing/chunking. **Effect:** `divinci-production-server-api`'s `event_loop_lag` metric hit **112 seconds p99** (mean 16.4s), `/health` itself timing out at 30s for stretches — this affected **all** prod traffic, not just WWW-RAG routes (a blocked Node event loop is service-wide). **How caught:** noticed `/health` timing out during routine post-connector verification, not from the connector's own logs (those just showed escalating generic errors on later hosts, which in hindsight were symptoms). Confirmed via the `event_loop_lag` structured-log metric specifically — health-check pass/fail alone was noted as an unreliable signal (can false-positive "recovered" on one lucky sample). **Resolution:** waited it out (~15-20 min) rather than a disruptive redeploy, since load was unevenly distributed across Cloud Run instances; confirmed no data corruption after. **Lesson, stated explicitly in the memory file:** *"A fixed sleep between REQUESTS is not pacing when the work each request triggers vastly outlives the sleep interval. ... any fire-and-forget 202-returning endpoint that kicks off heavy async work needs the CALLER to throttle on completion signals if firing it in a loop, not on submission timing."* The fix that followed gated each next host on the previous host's job reaching a genuine terminal state via polling, not a sleep.

### 4.9 A second, unrelated event-loop-lag spike — the "don't assume it's what you're testing" lesson
**What happened:** while re-testing the completion-gated connector rewrite, a second `event_loop_lag` spike hit prod (up to 890s on `/health`). It initially looked like a repeat of 4.8, but the timing didn't fit — the first spike appeared *before* the connector script's first API call. **Root cause:** an unrelated ScoredQA calibration cron sweeper was intermittently taking 80-890s per tick for a query that matched **0 candidates** — a no-op-on-empty-result-set handler taking 300+ seconds is the tell that the slowness is in the MongoDB layer/round-trip itself, not the handler's own logic (matches a previously-documented `DB_BACKPRESSURE` incident class). Corroborated by an unrelated concurrent endpoint also spiking. **Self-resolved** without any code change. **Lesson, stated explicitly:** *"don't assume a lag spike is caused by the thing you're actively testing just because the timing is close — check whether the spike's own handler's business-logic evidence... is consistent with that handler being the actual bottleneck."*

### 4.10 CPU-bound synchronous parsing blocks the event loop — timeouts don't help
**What happened:** even with correct one-host-at-a-time pacing (post-4.8 fix), a single host's crawl (man7.org) still blocked the event loop — `event_loop_lag` hit p99=209s during an 18-minute window where the job sat at 0 processed files. **Root cause:** `man7.org/linux/man-pages/dir_all_alphabetic.html`, reached within the first few crawl hops, is 1.86MB with 15,311 `<a>` tags. Per-page processing (cheerio DOM construction, a noise-removal pass iterating ~15 class/id patterns, Defuddle article extraction, and a link-extraction loop calling `new URL()` 15,311 times) is all **synchronous, CPU-bound work in one event-loop tick** — Node is single-threaded, so this blocks every other request the instance is serving for as long as it takes. **Why the earlier per-page fetch-timeout fix didn't help:** `pageTimeoutMs` races the scrape Promise against a `setTimeout` — that only works if the underlying work *yields* to the event loop periodically. Synchronous CPU-bound work does not yield; the timeout's own callback can't even run until the blocking code finishes on its own. **This is explicitly documented as a structurally different failure mode** requiring a different class of fix (a parsing-pipeline-internal guard or moving work off the main thread), not another Promise.race timeout. **Fix chain (took 3 profiling rounds to fully resolve):**
  1. First guess (750KB byte-size truncation) was insufficient — profiling found `extractWithDefuddle()` alone taking 12.25s on a 497KB page well under that threshold, because **Defuddle's cost scales with DOM complexity/nesting, not byte size** — byte truncation was "an imperfect proxy that never caught this case." Added `DEFUDDLE_MAX_BYTES = 150_000` (skip Defuddle above it, fall back to Cheerio-only extraction): 82% reduction on the test page (10.8s→1.98s).
  2. Still not fully clean on retest (7 crit spikes over 15 min). Further profiling found Defuddle's cost actually tracks **element/link count**, not byte size either — a 107KB page with 1,777 `<a>` tags cost 2.9-3.8s in Defuddle alone despite being under the byte threshold. Added `DEFUDDLE_MAX_ELEMENTS = 1000` (cheap `$("*").length` check) as a second independent skip trigger.
  3. Even with Defuddle correctly skipped, `node-html-markdown` itself scales super-linearly (measured 100KB→39ms, 300KB→485ms, 500KB→1.3s, 750KB→2.6s) — lowered `MAX_PAGE_BYTES` from 750KB to 300KB.
  Final measured result: max single-page cost 13.09s→2.09s (6.3×), full 19-page realistic batch 78.9s→18.6s (4.2×). **Live validation on the full arxiv.org crawl (25 min, 1,500 URLs, 185 chunks) showed 4 crit events total, all in the first 46 seconds, then completely clean — roughly two orders of magnitude improvement over the original incident.** **Lesson:** performance guards based on one proxy metric (byte size) can miss the actual driver of cost (DOM complexity, element count) — profile the real phase-by-phase cost on realistic pathological inputs rather than trusting an intuitive proxy threshold.

### 4.11 `POST /sync/cancel` is cosmetic — a cancelled job still swapped a broken vector live
**What broke:** `ConnectorSyncJobSchema.methods.cancel()` was just a DB write (`status="cancelled"; save()`) with no way to actually interrupt the in-flight crawl execution running in a separate async context (no `AbortController` threaded through). The crawl ran to its own natural end (or internal deadline), then unconditionally called `job.complete()` — silently overwriting the "cancelled" status — and, because the swap-trigger condition only checked `result.status !== "failed" && urlsDiscovered > 0`, **swapped the live release onto a broken partial vector** (78 succeeded / 1,422 failed chunks) despite the cancel API call having returned success. **How found:** discovered only by manually re-checking the live release *after* a "successful" cancel — not something the cancel API itself would ever have surfaced. **Fix:** `connector-sync.ts` now re-reads the job's *current* DB status right before finalizing; if something already terminalized it as cancelled, skip both the completion-overwrite and the swap (treat like a failed run — draft cleaned up, live release untouched). **This is explicitly scoped as a targeted fix, not a full fix** — the crawl itself still runs to completion server-side even after cancel; a true interrupt would need `AbortSignal` threading through the entire crawl call chain, deliberately not done here. **Lesson:** a "cancel" endpoint that only flips a database flag can create a race where a stale/aborted execution still commits its (bad) result — any cancel semantics need to be checked for right before the point-of-no-return, not just trusted at call time.

### 4.12 Cloud Run OOM kills — a job "stuck running forever" was actually dead
**What broke:** three separate crawl stalls (arxiv.org twice, avalon.law.yale.edu once) all traced, via `gcloud logging read 'textPayload:"Memory limit"'`, to **container OOM kills** at 2048 MiB — timestamps matched every stall to the second. **Mechanism:** heavy pages (6,000-10,000+ DOM elements, 500KB-1MB+ bodies) times `PAGE_CONCURRENCY=6` concurrent pages plus BFS frontier/visited-set memory for a 1,500-page crawl exceeded the container's memory limit; earlier per-page byte/element guards (§4.10) bound *per-page* cost but not *aggregate* memory across concurrent pages. Because the crawl runs as an un-awaited fire-and-forget continuation (`void runWebCrawlConnectorSyncPersisted(...).catch(...)`), the OOM kill left **zero chance for any catch/finally to run** — the job simply sat `running` forever with no error ever recorded, invisible without directly correlating memory-limit log lines against stall timestamps. **Fix (stopgap):** bumped Cloud Run memory 2Gi→4Gi via a new `CLOUD_RUN_MEMORY` env-var override (previously hardcoded, with a real separate gap discovered along the way — `deploy/config.json`'s per-service memory config was completely inert/never wired into the deploy script). **Not fixed (flagged as the real architectural fix):** moving web-crawl connector sync onto the same durable-execution pattern already shipped for file ingestion (a Workflow-based redesign), rather than a bare fire-and-forget continuation — this is the fix that actually prevents "silent job death with no error" as a *class* of failure, independent of what causes the death.

### 4.13 Instance recycling — the true root cause under the OOM fix, requiring durable re-invoke
**What broke:** even after the OOM fix, arxiv.org still stalled. Root cause, finally nailed via prod logs: `"Shutting down user disabled instance"` appeared ~2 minutes after crawl activity stopped — routine Cloud Run scale-down killing the fire-and-forget floating promise mid-crawl. **Fix:** migrated web-crawl connector sync to **Google Cloud Tasks durable re-invocation** — `enqueueWebCrawlSync` dispatches via Cloud Tasks REST, with a dedicated HTTP-target handler (`run-sync-task`) and shared-secret auth, plus a graceful inline fallback if Cloud Tasks isn't configured. **Activation was itself a multi-round debugging saga**: the new required secret (`WEB_CRAWL_WEBHOOK_SECRET`) was never actually configured in prod because prod's Infisical loader runs in single-path root-only mode and the secret lived in a folder — invisible to the app despite Infisical reporting "297 secrets loaded" successfully. **Side finding surfaced along the way:** the *existing* 6-hour web-crawl poll cron had been a silent no-op in prod this whole time for the identical reason. **Final proof:** re-fired arxiv.org and confirmed the full durable chain — Cloud Task enqueued, dispatched, handler hit with `Google-Cloud-Tasks` user-agent, 200 response, event-loop lag clean throughout. **Lesson:** "secrets loaded successfully" is not the same claim as "the specific secret my code needs is loaded" — when an env var mysteriously isn't in `process.env` despite a healthy-looking secrets-load log line, check *where* it's stored (root vs. folder) against exactly how the loader is configured to search, don't assume the loader's generic success log covers every individual key.

### 4.14 Embedding-fetch concurrency unbounded → silent chunk-level data loss
**What broke:** `PAGE_CONCURRENCY=6` throttled page *scraping* but the downstream embedding-fetch fan-out had its own zero cap — an N-page crawl could put up to N×(vectors-per-doc) concurrent Vertex AI embedding fetches in flight from one Cloud Run instance. **Effect:** connection-pool exhaustion causing **~64% chunk failure rate** on celestrak.org (174/270 failed) with generic `TypeError: fetch failed` (a pre-response connection-layer failure, not an application rejection) — independently reproduced on data.nasa.gov (16/216 failed), confirming it was structural, not content-specific. **Compounding finding:** failed chunks do NOT auto-retry — recovery requires manually calling a reconcile endpoint. **Fix:** a new rolling-concurrency `Semaphore` primitive gating the actual outbound embedding fetch at `EMBEDDING_FETCH_CONCURRENCY = 8`, placed at the one function every embedding caller (crawl, bulk-add, catalog-sync, dedup) funnels through — chosen specifically to avoid a scrape-loop-local fix that would leave other paths exposed. **A follow-on bug found in the fix itself:** the Semaphore released its permit correctly on rejection but not on a `fetch()` that just *hung* (no response, no error) — since the semaphore is a module-level singleton shared process-wide, a few hung fetches could permanently wedge *all* embedding work on that instance. Fixed with a 60s `AbortController`-based fetch timeout. **A genuine pre-existing repo bug discovered mid-fix:** `promise.ts` (flat file) and `promise/` (directory) are near-duplicate files in the same package; Node's module resolution silently prefers the flat file, so anything added only to the directory version (including the first attempt at this very Semaphore) was unreachable through the actual package export surface — cost ~30 minutes of "typecheck passes, runtime silently doesn't have the function" confusion. **Lesson:** concurrency caps placed at the wrong layer (per-page, not per-downstream-fetch) leave the real fan-out unbounded; and a semaphore/lock primitive must release on *every* exit path including hangs, not just rejections.

### 4.15 turso-libsql concurrent-DDL corruption
**Critical Turso Cloud finding, reproduced:** dropping and recreating a vector index corrupts the internal `libsql_vector_meta_shadow` table, causing *all future* vector queries in that database to fail with `"vector index(search): failed to parse vector index parameters"`. Heavy index churn (dozens of test create/drop cycles) in a shared Turso DB polluted it enough to eventually break all vector queries there — a fresh DB worked clean. **Fix pattern:** detect bulk-load state via index *absence* (never drop+recreate); build the index once, then only ever incrementally update it. This is also the strongest argument found for per-vector BYO databases (physical isolation) over a shared DB in production — one corrupted vector's DDL churn can't spread. A related concurrent-write finding on the same storage layer: arxiv.org's sustained crawl produced ~97% write failure (502s + some SQLITE_CORRUPT) against a turso-libsql draft vector, fixed with a per-table Semaphore + retry.

### 4.16 Boilerplate/duplicate-content pollution
**What broke:** page-level dedup never caught repeated header/footer/cookie-banner/newsletter blocks that appear on every page of a site. **Measured:** perldoc.perl.org 84.9% exact-duplicate chunks (a single footer repeated 233×), justia.com 30.9%, postgresql.org 21.1%, planet4589.org 22.5%. **Fix:** applied twice — a crawler-side per-host chunk dedup (keep first occurrence) and an `ingest-okf`-side flatten dedup that retro-cleans existing bundles at embed time, so already-crawled sites benefit without a re-crawl. **Result:** perldoc's chunk count dropped from 33,251 → 5,035 (an 85% reduction) after republishing. **Lesson:** a RAG corpus's "chunk count" metric is meaningless (even misleading) without a duplicate-content audit — a site can look 6× richer than it is purely from repeated boilerplate, degrading both retrieval quality and embedding cost.

### 4.17 Thin-content hallucination — a wrong identity is worse than a bland fallback
**What happened:** an LLM-based release-enrichment pass (generating a welcome message + starters from a site's crawled content) was applied to www.nuforc.org, a JS-heavy report portal that had only 2 crawled pages (homepage 301-redirected). The LLM **ignored the sparse-but-accurate context** (page titles clearly said "National UFO Reporting Center") and invented a confidently wrong identity — "take charge of your health and well-being" — apparently free-associating from the domain name's phonetics. This matches a separately-cited incident of the system once calling a UFO-sighting-reports archive a "health & wellness" site when auto-generating a public site description with insufficient real content to ground it. **Fix:** manual `--welcome`/`--starters` override flags that skip the LLM and hand-set safe, title-derived content for known-thin sites, PLUS an automatic content-floor guard added directly to the release-enrichment tool: gate LLM enrichment on page-count/body-char thresholds and fall back to a title-derived welcome automatically when content is thin, rather than relying on someone noticing after the fact — verified fixed against the real nuforc.org case (now correctly identifies as "National UFO Reporting Center"). **Lesson, stated directly:** *"a wrong identity is WORSE than the templated fallback... never trust generative enrichment on thin crawls."*

### 4.18 Headless-Chrome process leaks → OOM
Render-fallback launches a headless Brave instance per thin/JS page. Without an explicit reap, these processes leaked and accumulated across passes — this is cited as "the historical OOM crash" pattern for the loop. Fixed with a reaper (`reap_headless_brave`, pkills only `--headless`-flagged Brave processes, run before each pass and after ingest — carefully scoped so the user's normal GUI Brave, which never carries `--headless`, is untouched and verified 0 headless / 18 GUI procs after a real run). A related acute case: 71 orphaned headless-Brave-Helper processes held ~3.5GB RAM after one render-heavy crawl, OOM-killing the subsequent `ingest-okf` (which loads all bundles at once) twice before being manually `pkill`-ed. The reap was subsequently tightened a second time to match the daemon's own precise temp-profile pattern (`rust-headless-chrome-profile`) rather than a broader match, after confirming via `pgrep -f` inspection that the broader pattern could theoretically have risked matching a user's real browser session.

### 4.19 Local libSQL shadow-row corruption from unclean shutdown
Two hosts (hsgac.senate.gov, planet4589.org) independently hit `"vector index: failed to init meta table"` — traced to local `.turso/<host>.db` file corruption, likely from an interrupted write (disk sleep, unclean process kill). Both required deleting the local DB and letting the next pass re-embed from the `okf/` source-of-truth bundle (cheap, since OKF is the canonical artifact and the vector store is explicitly a rebuildable cache over it). **Lesson generalized into the loop's own hardening:** `assert_lock` phase gates were added specifically to prevent concurrent `ingest-okf` runs (a second cause of the same corruption class), and an external-drive migration doc explicitly calls out that if the corpus is ever moved to a drive that can sleep/unmount mid-write, expect the same corruption.

### 4.20 Static-only product extraction — coverage gaps discovered via a real e-commerce test
Testing the JSON-LD product-catalog extractor against a real WooCommerce demo store (scrapeme.live) surfaced two structural limits: (1) the extractor is static-HTML-only (reads JSON-LD from the raw fetched HTML) — SPA stores that inject product JSON-LD client-side yield 0 products even with the render tier on, because render mode still reads from the pre-render static DOM for this specific extraction path; (2) a "thin listing page" bail (the crawler stops following links from pages with 0 extractable chunks) meant grid/pagination pages weren't traversed, so only 34 of ~750 real products were found without manually seeding a product detail page. **Fix:** the thin-listing bail was loosened to still follow links from *successful*-but-chunk-empty pages (only genuinely *failed* fetches dead-end now), plus sitemap-following was added as a more reliable seeding source for e-commerce coverage. **Explicit conclusion recorded:** crawl-derived JSON-LD product catalogs are "opportunistic, not authoritative" — for complete demo catalogs, prefer sitemap/feed import over crawl discovery.

### 4.21 SSRF via crawled product image URLs
**Security finding during the same product-catalog work:** the `register-products` endpoint stored `imageUrl` values taken directly from untrusted crawled JSON-LD, which was later fetched server-side by the R2 image-download pipeline unguarded — a malicious site could set `image=http://169.254.169.254/...` (cloud metadata endpoint) to trigger SSRF via image download. **Fix:** a `sanitizeProductUrl()` pre-store filter dropping non-http(s) schemes and private/loopback/link-local IP literals, plus a defense-in-depth `ssrfSafeFetch` (blocks private IPs, pins DNS against rebinding, re-validates redirects) at the actual fetch layer. **A process mistake made during the fix's own verification, flagged explicitly:** the engineer POSTed a real `169.254.169.254` payload to **production** to confirm the vulnerability existed before the fix was live, rather than testing on staging or with an inert payload — stored raw, then deleted immediately, but explicitly logged as "DON'T inject attack payloads into prod to test a security fix."

### 4.22 R2 export — planned, never wired ("if the laptop dies, the deep local corpus is gone")
A cold-archive step (rclone-syncing the local crawl corpus to an R2 bucket) was designed and documented as a TODO in a phase-2 runbook, and the target bucket (`divinci-wwwrag-okf`) was even provisioned — but the actual sync call was never added to `crawl-loop.sh`, and `rclone` isn't installed on the crawl machine. **Nothing has ever synced.** Separately, an *unrelated* R2 pipeline for a different project (PixelRAG's visual-tile uploads) is confirmed working — useful only as a "no, the tooling for this class of upload works fine elsewhere, this specific integration was just never finished" data point. **Explicit bottom line recorded:** if the local crawl machine were lost, only content already *published* into platform vectors would survive — the deeper local crawl corpus (the un-published depth, and the historical record) has no off-machine backup. As of 2026-07-14 this was consciously accepted as a residual risk (published data lives in Turso Cloud = off-machine; local `okf/` is "regenerable by re-crawl" in theory, though a full re-crawl of ~90+ sites is not a small undertaking).

### 4.23 D1 orphan accumulation (adjacent infra hygiene finding)
While investigating vector cleanup, discovered that Cloudflare's D1 database count (`~1,032` databases total account-wide) vastly exceeded the number of live worker scripts that should own them, initially estimated at ~989 orphans. A proper cross-environment reconciliation tool (unioning live RagVector IDs across staging+prod Mongo) found the real number was much smaller — **38 true orphans**, not ~989 — illustrating that a worker-count-based orphan estimate was simply wrong. Deleted cleanly after a dry-run. **Lesson:** back-of-envelope orphan estimates from a mismatched proxy metric (worker script count vs. actual live-resource count) can be off by an order of magnitude; a real reconciliation against the authoritative live-resource list is worth building before deleting anything.

## 5. Open questions / unresolved decisions

- **Native-connector-migration status:** the platform Web Crawl Connector is fully built, deployed, and proven durable (all 6 identified failure modes fixed: script race, embedding-pool exhaustion, semaphore permit-leak, Cloud Run OOM, turso-libsql concurrent-DDL corruption, durable Cloud Tasks re-invoke) — but the explicit 2026-07-14 decision was to use it only as the **customer-facing** self-serve crawler, not as WWW-RAG's own bulk-ingestion vehicle. WWW-RAG's own corpus growth stays on the local Rust daemon. This could reverse if the local-machine approach hits its own ceiling (disk, single point of failure, thermal limits on a laptop).
- **R2 cold-archive:** designed, bucket provisioned, never wired into the loop. Open risk: local crawl depth (beyond what's published) has no off-machine backup.
- **Loop autonomy / scaling plan:** as of the most recent notes, the corpus growth was still semi-manual per new site (research → crawl → publish → register), with a fully autonomous day/night loop only recently hardened (dedup-via-directory-API fix, disk-headroom guard, Brave reaper) — whether/when it runs fully unattended long-term wasn't confirmed finished.
- **Theme coverage:** per-host brand-theme extraction (color palette + fonts scraped from the live site) was built and proven, but coverage across the ~90+ site corpus was still ~1 host at last note — needs a dedicated render-enabled sweep pass.
- **Font application:** captured but deliberately not applied client-side yet — `WebSafeFont` collapses real fonts to generic substitutes (e.g., Karla → Arial), judged low-value until the theme schema supports real web fonts.
- **Release enrichment for future new sites:** wired into the pipeline for new sites, backfilled for the existing corpus at time of writing — ongoing maintenance item as new sites join.
- **Product-catalog extraction:** explicitly "opportunistic, not authoritative" — real e-commerce demo coverage needs sitemap/feed import, not crawl-discovery, as the primary path.
- **DGX Spark / AMD AI Halo fleet plan:** a multi-machine embedding-accelerator fleet design exists (docs in the repo) as the next scale step beyond one MacBook, but hardware wasn't yet in hand as of the plan's writing.
